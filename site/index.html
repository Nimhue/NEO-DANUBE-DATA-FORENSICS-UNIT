Briefing · how the unit is built

Five schemas, four cases, one sealed answer

Preserve before you analyse. Record every repair. Never accuse on one weak signal. Undo surgically.

A seeded generator builds a fresh crime scene in a Unity Catalog volume: damaged shard files, a ledger with 14 days of commits, identity records from four systems that don't agree, and an answer key sealed before the investigation starts.

Each case is a Databricks notebook backed by tested Spark functions in src/. The last job task opens the sealed key and fails the run if the unit got the answer wrong. The tests grade the detective, not just the code.

  • Same seed, same crime. New seed, new crime, still solvable.
  • Four difficulty levels: street_kid, corpo, nomad, legend.
  • Runs as an Asset Bundle job on serverless, or notebook by notebook in Free Edition.

Case 01 · Shard recovery

Ghost in the bytes

The courier's shard holds the ledger as it was before anyone touched it. Our most honest witness, and it's badly damaged.

The fragments arrive in three shapes: JSON from newer firmware that renamed fields, CSV with unquoted commas, and CSV from an old deck that writes latin-1. Some lines are truncated mid-record, some are pure static, and some records were sent twice.

The rule is simple: recover what you can, record how you recovered it, and never invent a value. Every record ends in one of five tiers.

  • Auto Loader with an explicit schema and trigger(availableNow=True)
  • _rescued_data catches the renamed amt field and string amounts
  • columnNameOfCorruptRecord keeps truncated lines for salvage
  • binaryFile + decode(content, 'ISO-8859-1') for the legacy deck
  • Rebuilding misaligned CSV rows, deduplicating with a window

Case 02 · The tamper

Someone rewrote history

Every commit says "routine reconciliation". Delta Lake keeps the receipts anyway.

Each bar below is one Delta commit to the ledger. Drag through versions and watch the sample transactions change. Honest edits turn cyan. Malicious ones flash magenta.

Change Data Feed gives a before and after image for every changed row. Every change is scored: strong evidence is worth 2 points, weak hints 1. A change is tampering at 2 points or more, because the night shift really does work at 1 a.m.

  • DESCRIBE HISTORY: commit-level metadata and operation metrics
  • Time travel with VERSION AS OF
  • table_changes(): update_preimage / update_postimage pairs
  • Commit-level attribution, since a delete row shows the victim's last editor
  • SHALLOW CLONE as a sandbox, RESTORE vs a surgical MERGE

Case 03 · Ghost identities

Who's the real merc?

The edits were signed by operator logins nobody in HR recognises. Four identity systems, one person wearing several faces.

Every dot is an identity record. A line means two records scored above the match threshold. Records that connect, directly or through a chain, are one person. The ghost logins are ringed in yellow.

Drag the threshold. Too low and lookalikes (same surname, same district) merge into one person. Too high and the culprit's aliases fall apart.

  • Normalize: lowercase, translate accents, sort name tokens
  • Blocking keys so you compare a few percent of pairs, not all of them
  • Weighted scoring with levenshtein; day/month-swapped DOBs; one-digit-off IDs
  • Connected components by label propagation, no GraphFrames needed
  • Golden records with survivorship rules (civil registry wins)

Case 04 · The trail

Follow the money

We know what changed and who changed it. Last question: where did the eddies go?

Every finding becomes an edge: person → signed as → login → edited → transaction → paid to → account → owned by → person. Stored as a plain Delta edge table, it feeds this graph, a dashboard, or GraphFrames later. Hover a node to trace its path.

Governance · clearance levels

Need to know

Same table, same query, two different answers. Unity Catalog decides at read time.

A column mask is a SQL function attached to a column; a row filter is one attached to a table. Unity Catalog applies them on every read, from every tool: notebooks, SQL warehouses, Power BI.

Rookies see redacted IDs and dates of birth, and the prime suspect's row simply isn't there. Detectives (members of dfu_detectives) see everything. Tags record the chain of custody; lineage shows the path back to the raw shard files.
